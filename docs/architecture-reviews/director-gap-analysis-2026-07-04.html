Director gap analysis

penroseart · master @ c3176c07 (OSC schema v2) · 2026-07-04 · rev 2 (2026-07-05, clarified model)

Intended model: the Director is a watcher. It watches the timing_grid plus the current and next phrase — either can change at any time. Phrase change → rebuild the Cue Sheet immediately (cheap, because sheets carry marks only). Entering Synced Mode may mean building two sheets at once; steady state builds one at a time. Per cue it casts effect + transition from Repertoire and what's coming up, sends to the Switcher, and keeps re-directing until the Switcher says locked — the only word the Switcher ever says back. No phrase data → cue off the timing grid. No timing grid → Standalone Mode. One rung, not fallbacks-for-fallbacks.

Watch both phrases; rebuild sheets the moment either changes

gap in-process

Assets/core/Switching/CuePlanner.cs · CueSheet.cs · PhraseWindow.cs

Now — demand-driven, next phrase is branch 5 of 5

  1. Beat < 1 → Unlocked
  2. Held-open mandatory boundary
  3. Live phrase window → build/reuse sheet
  4. Held sheet still covering its window
  5. Next phrase → build ahead (only reached when 3–4 fail)

While a live phrase serves branch 3, the announced next phrase is ignored. The fresh sheet appears at the turnover beat. Commit a455b80b deleted the second-sheet lifecycle.

Intended — the Director watches

  • · Watch phrase_state and next_phrase_state — either can change at any time
  • · Any change → rebuild that sheet as fast as possible
  • · Entering Synced from Standalone → build both sheets at once
  • · Steady state → one build at a time

Rebuilds are cheap by design: sheets carry marks only, never casting. That's the whole reason effects/transitions aren't assigned at build time.

Problem: the planner resolves sheet identity per beat instead of watching the two phrase signals; a mid-phrase change to the announcement isn't noticed until turnover, and there's no two-sheet state to promote from.

Solution: hold current + announced sheets keyed on their phrase identity; rebuild eagerly on any change in either signal; promote announced → current at turnover. CueSheet.Build stays untouched.

  • · Sheet identity = phrase event
  • · DJ changes land before turnover
  • · Branch-5 fallback deleted

The Director stops directing after it sends

gap in-process

Assets/core/Switching/Director.cs:617-790 · CuePlanner.cs:241-246 · Switcher.cs:293-311

Problem: after CommitSentCue, consumed-mark memory makes every later beat for that mark return Wait, and the cursor advances past it — the Director never re-reads Fill/Drop/Energy for the loaded cue. If the DJ changes the song between send and lock, the cue fires stale.

Solution: each synced beat, while the Switcher answers not locked and the loaded mark is unchanged, re-run event intent + casting off the timing grid and what's coming up; upsert only when the decision differs. The Switcher side already exists and is idle: the replace-unlocked branch and SameCue (Switcher.cs:515-531) were built for exactly this.

  • · Live event stays live
  • · Latent Switcher interface earns its keep
  • · Lock stays the single point of no return

Addendum: the live hard cut is late-commit backdating — not a rogue Director

gap confirmed live symptom

Switcher.cs:349-374,432,546-551 · TransitionBeatPlan.cs:37-40 · CuePlanner.cs:113-160,239-251 · Director.cs:571-585,792-824

Ruled out: the Director never mutates transition timing (no transition analog of the effect overrides exists), and no saved TransitionSettings asset is 0/0 — saved runway/tail: Fade 4/0, DirectionalWipe 5/0, IndexWipe 4/0, Iris 1/4, Noise 4/1, Fizzle 4/1, RGBFade 5/1. The explicit zero-duration cut branch is unreachable with current data.

Mechanism: the Switcher anchors the timer to the musical start (StartBeat = CueMark − Runway), but the cue window accepts commits from StartBeat through CompleteBeat. Commit on the impact beat and the start is already Runway beats in the past — progress backdates to Runway/(Runway+Tail) on the first frame. For a zero-tail transition that is 1.0: a real transition "ran," the wall showed a hard cut. The strongest intermittent trigger: the planner holds a mark open past impact sized by the staged transition's tail, then the deck commits a different, zero-tail transition. Drop cues without drop-protect land it on the drop beat — the most visible moment.

The intended execution model (clarified 2026-07-05)

The Cue Mark is planning vocabulary only — it names where impact lands, and the runway/tail split decides whether the move is front-loaded or back-loaded around it. Execution never works "off the cue mark":

  • StartBeat = CueMark − RunwayBeats
  • duration = (RunwayBeats + TailBeats) × avg-beat-ms
  • fire ON the start beat · lock one beat before · timer runs · done

One rule makes it true: a cue must commit before its lock point. Too late for the selected transition's runway → it does not cue (next mark, or a shorter-runway transition; fail plainly). That deletes the late-commit window, the backdating math, and the planner's late-cue-window plumbing — the accreted tolerance for skipped OSC beat frames that a watching Director no longer needs.

  • · Hard cuts become impossible by construction
  • · Switcher shrinks to load → lock → timer → fire
  • · Rides along with watch-until-lock

No phrase → cue off the timing grid (the one rung that should exist)

gap in-process

CuePlanner.cs · OnAirTiming.cs:22-75 · BeatManagerQueries.cs (Grid) · RaveOscSnapshot.cs (timing_grid, iis)

Now

  • · No phrase data → Unlocked frames → zero cues for the whole track
  • · timing_grid arrives on the wire (beat 1–16 = the One, bar, locked/coasting/disputed) but the Director/planner never reads it — HUD only

Intended ladder — three rungs, no more

  1. Phrase data → Cue Sheets (the real model)
  2. No phrase → cue on the timing_grid One
  3. No grid → Standalone Mode

Solution: add timing_grid to OnAirTimingInput; when both phrase queries are null, target the grid's next One on the 16-beat cadence. No synthetic phrases, no coasting, no fabricated windows — the grid is real wire data, and the grid is what the Director should be watching anyway.

One deliberate decision rides along: "no timing grid → Standalone" makes timing_grid presence the Synced/Standalone authority. Today the authority is beat_in_bar ≥ 1 (ADR-0007). If the grid becomes the gate, amend ADR-0007 explicitly rather than letting two authorities coexist.

What already matches the model — don't rebuild it

matches

CueSheet.cs · Director.cs:629-790 · Switcher.cs:364-447 · Deck.cs

Cue placement (CueSheet.Build)

  • · 16-beat grid (DefaultGridBeats = 16)
  • · Random interior count, uniform over [0, N] inclusive, drawn without replacement
  • · Mandatory final mark at phrase end — always
  • · Gaps > 64 beats filled at previous + 64
  • · Marks are timing only — the deliberate cheap-rebuild design

Cue commit + lock (Director / Switcher)

  • · Casting happens at the commit point, per synced beat
  • · Reads live Fill/Drop: Drop, DropApproaching, Fill intents; drop-protect keeps a HandlesDrop performer on stage
  • · Energy biases casting, always behind event intent
  • · Deck cards pulled only when a cue is actually sent
  • · Lock = one beat before runway start; locked = immutable; fires unconditionally

These modules are deep: small interfaces (Plan → TimingFrame, UpsertLoadedCue) hiding real behavior. The intended model lands as a re-wiring of triggers, not a rewrite.

Shrink the Switcher's answer to one word: locked

partial

Switcher.cs:200,580-591 · Controller.cs (HUD) · Assets/Editor/ControllerEditor.cs:336

Problem: execution is already fire-and-forget (the Director never polls Loaded/Started lifecycle — good). But the Switcher's interface is wider than the model wants: SwitcherStatus and SwitcherCueStatus publish source/target/progress/cue detail consumed by the HUD and inspector, and CanUpdate is read only by the editor panel. The intended contract: the Director asks locked?; nobody else asks the Switcher anything.

Solution: the runtime seam becomes UpsertLoadedCue / AbortLoadedCue / Render + IsLocked. Observability moves behind the Director's own status (the observatory already reads the Director's last Cue Decision, 847bf9ed) — inspectors follow the runtime, never the reverse, per the repo's own rule. Interface shrinks; implementation absorbs the status plumbing.

  • · One caller, one question
  • · Locality: cue truth lives in the Director
  • · Pairs with watch-until-lock

One seam for effects/transitions to pull beat data

gap in-process

Assets/core/Effects/EffectBase.cs · Assets/core/Rhythm/BeatManagerQueries.cs · Assets/effects/**

Problem: effects evolved alongside the OSC stack, so each pulls BeatManager data its own way — direct GetBeatBrightness(variant, max, min, enable) calls with hand-swapped min/max for inverted pulses, ad-hoc query mixes — while the existing EffectBase.BeatBrightness()/BeatTime() wrappers sit unused by every effect (too rigid: fixed max, hardcoded time base). Same plumbing, duplicated ~26 times in slightly different shapes. Transitions are about to join in as they gain fill/drop behavior — without a seam, they'll duplicate it again.

Solution: audit the real pull patterns across the 26 effects (there are only a few genuine shapes), replace the dead rigid wrappers with helpers that cover those shapes, and keep the contract two-sided: Repertoire advertises what an effect/transition supports; the shared seam is how it pulls; the effect alone decides how to use it. Deduplicate plumbing, not creative decisions.

  • · Leverage: one interface, 26+ call sites
  • · Transitions inherit the seam for free
  • · Delete the unused wrappers

Needs its own audit pass first: this review counted the duplication but did not catalog every effect's pull pattern. Design the helpers from that catalog, not from speculation.

Top recommendation

The three red gaps are one defect: the Director decides once and stops watching. Fix it as one watch loop, in this order — re-direct the loaded cue until the Switcher says locked (the Switcher half is built and idle; touches one seam) — and with it the commit-before-lock rule that kills the live hard-cut bug — then watch both phrase signals and rebuild sheets eagerly, then add the timing-grid rung for phrase-less tracks. The shared beat-data seam is the parallel track — it unblocks the repertoire coverage work that gives the watching Director something to cast.
