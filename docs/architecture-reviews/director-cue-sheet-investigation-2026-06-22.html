Verdict Partial match In-process modules

The current code has a hidden cue-sheet-like module for where cues may land, but it does not yet have Hunter's explicit loaded cue model for what will fire and when it becomes immutable. The resolved target flow is now captured in docs/adr/0005-phrase-cue-sheets-and-armed-cues.md.

Matches

Upcoming phrase data can pre-plan selected Phase Boundaries; the phrase end is mandatory; the next target can load while a Tail still renders.

Differs

Cue sheet identity is exact start/end/length, not length-only; effects/transitions are chosen just-in-time; no one-beat lock exists.

Resolved decision

A Cue Mark is the Transition Impact target. The Lock Point depends on the selected Transition's Runway; the Switcher needs one Armed Cue state, not a preload queue.

Hunter's target model, normalized into code terms

Phrase-level cue sheet

flowchart TD
  U[Upcoming Phrase changes] --> L[Read length in beats]
  L --> P[Divide into 16-beat Phases]
  P --> R[Randomly choose some Phase marks]
  R --> E[Always add phrase end]
  E --> S[Store CueSheet for upcoming]
  S --> T[Upcoming becomes current]
  T --> C[Use stored CueSheet]

The Cue Sheet is simple: relative Cue Marks for where transitions should land. It should survive sudden metadata changes when the total length is unchanged.

Cue-level loaded state

flowchart TD
  C[Current CueSheet] --> N[Pick next mark only]
  N --> D[Choose effect + transition]
  D --> M[Mutable LoadedCue]
  M -->|phrase data changes before lock| D
  M -->|Transition-specific Lock Point| K[ArmedCue]
  K --> F[Fire no matter what]
  F --> X[Choose next cue]

One cue is prepared at a time. After the Lock Point, phrase changes must not alter the Armed Cue. After fire, the next cue may be loaded even if the previous Transition Tail is still rendering.

Differences from the desired cue-sheet model

1. The cue sheet exists, but under a different name and identity rule

Closest match in-process

Desired
CueSheet

same length ⇒ same sheet
Current
SelectedPhaseBoundaryPlan
Start + End + Length
absolute boundaries sorted
same length but shifted start/end ⇒ plan does not match
What current code does
  • SelectedPhaseBoundaryPlan.Build randomly selects eligible interior Phase Boundaries and always adds window.EndBeat.
  • OnAirTiming.SelectedPhaseBoundaryPlans stores one current cursor plus one upcoming plan.
  • Upcoming plans are created from TrackPhaseActive == 0; current plans come from TrackPhaseActive >= 1.
Mismatch
  • Hunter's model says total length is the only invalidation rule.
  • Current Matches requires PhraseStartBeat, PhraseEndBeat, and PhraseLengthBeats.
  • A sudden same-length timing shift can reroll the plan.
Implementation move: replace the absolute identity with a relative CueSheet module: LengthBeats + relative mark offsets. Instantiate it against the current phrase start when needed.

3. Cue content is not loaded and locked one beat early

Major mismatch in-process
Files: Director.cs:452-517, SyncedCueIntent.cs:60-128, TransitionBeatPlan.cs:3-39
Desired loaded cue lifecycle
flowchart TD
  A[Pick first cue mark] --> B[Choose Effect + Transition]
  B --> C[Mutable LoadedCue]
  C -->|changes allowed| B
  C -->|one beat before trigger| D[Locked LoadedCue]
  D --> E[Fire no matter what]
Current just-in-time cue
flowchart TD
  A[Every synced beat] --> B[Read TimingFrame]
  B --> C[Evaluate staged Effect + Transition]
  C --> D{inside runway?}
  D -->|no| W[Wait]
  D -->|yes| S[StartTransition immediately]
  S --> N[Stage next random choices]

SyncedCueIntent.Evaluate builds a beat plan from the selected Phase Boundary and the currently staged transition, waits until the current beat is inside that transition's runway, then returns a cue. The Director immediately calls StartSyncedTransition.

Missing interface

No LoadedCue module records mark, effect, transition, lock beat, and fired state.

Missing invariant

There is no code path that says "at the Transition-specific Lock Point, this cue cannot be changed anymore."

Implementation move: add a Director-facing LoadedCue state machine. Tests should hit the Director seam: mutable cue can be replaced before lock; locked cue fires despite phrase changes.

4. The Switcher needs Armed Cue state, not a preload queue

Design gap in-process
Files: Switcher.cs:189-281, DirectorSyncedTailTests.cs:97-122
Current Switcher interface
StartTransition(target, transition, timing)
mutates transition A/B · calls OnStart · sets duration · starts rendering now
Desired Switcher role
Own one Armed Cue
use Runway/Tail to start and progress · no multi-cue queue
What current code does well
  • It can start a new transition while one is rendering by using the previous transition's B as the next source.
  • After StartTransition, RenderAtTime only progresses by stored start time and duration.
What is missing
  • No Armed Cue state.
  • No arm vs start distinction.
  • No Lock Point invariant in mechanical execution.
Implementation move: keep the queue out. Add a single Armed Cue execution state so the Switcher can own Runway/Tail start/progress after the Director locks and arms one Loaded Cue.

1. CueSheet

Length + relative marks; always include length.

2. Promotion

Upcoming sheet promotes by length, not exact identity.

3. LoadedCue

One cue owns mark, transition, effect, lock beat.

4. Lock

Before lock: replaceable. After lock: fires.

5. Switcher

One Armed Cue slot; no preload queue.

Resolved before implementation: Cue Marks are Transition Impact targets, not transition start beats. The Switcher derives StartBeat = ImpactBeat - RunwayBeats; the Lock Point is Transition-specific, one committed beat before that start. ADR 0005 records this flow.

Tests to write first

  • CueSheet.Build returns relative marks and always includes phrase length.
  • Same phrase length reuses the existing upcoming sheet even when start/end shift.
  • Different phrase length regenerates the upcoming sheet.
  • Upcoming sheet promotes to current without rerolling.
  • Loaded cue can change before lock.
  • Loaded cue cannot change at/after Lock Point.
  • Armed cue fires even if Track Phase suddenly changes.
  • Next cue loads while previous Tail is still rendering.

Bottom line

Do not throw away the current On-Air Timing work. It already has the right deep module shape for phrase planning. The fix is to make the hidden selected-boundary plan truthful as a CueSheet, add a small LoadedCue interface in the Director, then hand one ArmedCue to the Switcher at the Transition-specific Lock Point. No multi-cue preload queue is needed.
