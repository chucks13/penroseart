The Director — what it is, what it does, where its data comes from

Branch director-event-aware-cue-intent · grounded in code, 2026-06-24 · runtime architecture, not a deepening review

In one sentence: the Director is the per-frame decision layer that, every frame, reads available musical timing, decides what Performer plays next and when the change should land, and hands one fire-and-forget cue to the Mechanical Switcher — which is the only thing that actually moves pixels. The Director directs; the Switcher executes. Everything else on this page is the machinery that feeds that decision or carries it out.

1 · Big picture — one decision, fed by many subsystems

The Director sits in the middle of a one-directional pipeline. Live music enters on the left, a rendered 900-tile frame leaves on the right. The Director itself holds almost no music interpretation — it asks On-Air Timing for a digested Timing Frame, asks Synced Cue Intent whether to fire, and tells the Switcher what to do.

The Director's whole contribution is step 3 — and it is purely a decision. It never writes pixels; step 4 (the Switcher) is the only thing that produces the Color[] buffer.

4 · The Director's job, split three ways

Tick() branches on one fact: is there a live beat source? IsSyncedMode ⇐ controller.beatManager.IsLiveSource. Hold is layered on top of either. None of these is a "fallback" — Standalone is an equally intentional self-running mode.

Synced Mode

Live OSC present. The Director asks On-Air Timing for a Timing Frame and lands changes on musical Cue Marks. Anticipatory: a transition starts early so its Impact Point lands on the beat.

TickSyncedMode(beat)

Standalone Mode

No live OSC. A wall-clock Timer drives cadence; OnTimerFinished() picks the staged next move and starts it immediately. Timer expiry is ignored while Synced.

TickStandaloneMode(dt)

Hold

An inspection freeze. A non-negative heldEffect pins one Effect and suspends the Director — no rotation, no cues — so a developer can tune it live. -1 = Random = normal rotation.

controller.TryGetHeldEffectIndex()

Staging. The Director always keeps a concrete NextEffectIndex and NextTransitionIndex so the Tuning Window can show what's coming. Manual selection (SetNextEffect/Transition) is a one-shot override; "Hold Selected" keeps the staged choice across moves. Both Standalone and Synced consume the staged choice when a move actually fires.

5 · Where the Director gets its data

Every musical fact the Director uses originates in BeatManager, fed by live Rave OSC. The Director and On-Air Timing never read raw OSC payloads — they read BeatManager's nullable contrived queries (ADR-0002), where null always means "not available right now", never an error.

raw beat transport — consumed by On-Air Timing

  • Beat — absolute beat, 1-based ("the one"); may rewind on a looped track
  • TotalBeats — track length in beats
  • BeatInBar — 1-based beat label within the bar
  • Phrase() → Track Phase: inPhrase, beatsUntilNext, lengthBeats (tri-state: active / announced-upcoming / absent)
  • BeatFraction / IntraBeatFraction() — sub-beat progress, for smooth backdating

phrase events — consumed by Synced Cue Intent for casting only

  • Fill() → PhraseEventInfo? — inProgress, beatsUntilStart/End, length
  • Drop() → PhraseEventInfo? — same shape; Drop wins ties
  • Energy() → EnergyInfo? — Low/Mid/High. Query kept, but no longer drives Director casting (see §8).
  • Levels() → band energy — for effects, not the Director
The red rule: Fill/Drop/Energy data is read by the Director only to choose which Performer to cast. It must never create, move, or delay a Cue Mark. Timing comes from the phrase structure (Cue Sheet); events only bias selection. Effects pull the live Fill/Drop data themselves and own how they react.

RaveOscReceiver.ApplyTo(beatManager) runs first each frame: it sets IsLiveSource from a liveness grace-window and deep-copies the latest on-air snapshot into BeatManager. When OSC stops, IsLiveSource goes false and the Director drops to Standalone — by preference, not degradation.

6 · On-Air Timing & the Timing Frame deep module

This is the deepest module in the system: a wide, messy implementation (phase locking, phrase windows, cue-sheet cursoring, loop-rewind correction, coasting) behind one narrow interface — ReadFrame(input, passLocalState, minCadence) → TimingFrame. The Director consumes only the Timing Frame; it holds none of this machinery itself.

The Timing Frame carries

  • CurrentBeat, Phase reading
  • HasPhaseAnchor + PhaseAnchorConfidence
  • CueMarkBeat + BeatsUntilCueMark — the target to land on
  • PhraseWindow (when Track Phase known)
  • Source — why this target exists
  • BeatRewoundToNewPass + pass-local state correction
  • Coast / Reanchored flags + CueSheet status

Timing source, strongest → weakest

  • Structural — Track Phase active: Cue Marks from the live phrase
  • TrackPhaseBoundary / CueMark — sheet-driven targets
  • Coast — Track Phase vanished; advance the last anchor in 16-beat steps
  • PhaseClockGrid — beat known, no phrase: plain 16-beat grid
  • Unlocked — nothing to target; invents nothing

Phase Clock confidence tiers

  • Structural — beat + active Track Phase + length → exact phrase "one"
  • Closed — beat + total beats → grid recovered from track end
  • Open — beat only → assume beat 1 is the one
  • Provisional — bar position only → a guess
  • Unlocked — nothing usable

Self-correction (loop restart)

Live Beat can rewind when a track loops. A backward jump ≥ the 16-beat minimum is treated as a new pass: the cursor rewinds, stale pass-local cue/cadence state at-or-after the new beat is cleared, and the Director is told so it doesn't let an old beat block the new loop. Tiny 1–2 beat backsteps are OSC jitter and ignored.

Internally, two private classes do the heavy lifting: CueSheetPlans holds a current sheet plus a pre-planned upcoming sheet (built early from the announced next phrase, promoted at the boundary), and CueSheetCursor walks Cue Marks within one sheet. Reuse rule: a sheet is kept when the new phrase's length matches (Matches), regenerated otherwise.

7 · The Cue Sheet — a phrase timing plan, nothing more

A Cue Sheet is a list of phrase-relative offsets where a change may land. It is pure timing structure: it stores no effect choices, no performer choices, no event labels. CueSheet.Build():

Worked example. A 64-beat phrase has interior candidates at +16/+32/+48 (three — the +64 end is mandatory, the start is excluded). So 0–3 random interior marks plus the guaranteed end mark.
No near-end marks. An earlier experiment added timing-only marks 8/4/2 beats before phrase end to "represent Fill timing". That fired cues mid-phase and was removed. The current sheet has only 16-beat boundaries + the mandatory end + 64-beat gap fills.

8 · Cue intent & event-aware casting

Once On-Air Timing produces a Cue Mark, SyncedCueIntent.Evaluate() answers two questions: should we fire on this beat? and who should we cast?

sequenceDiagram
  participant D as Director.TickSyncedMode
  participant T as OnAirTiming
  participant I as SyncedCueIntent
  participant K as EffectDeck / TransitionDeck
  participant S as Switcher
  D->>T: ReadFrame(input, passLocal, minCadence)
  T-->>D: TimingFrame (CueMarkBeat, anchor, source)
  D->>I: ResolveEventIntent(frame, Fill, Drop)
  I-->>D: Ordinary | Fill | Drop
  D->>I: Evaluate(frame, repertoire, intent, staged, deck)
  Note over I: gate = HasPhaseAnchor · IsCueBeat(runway) · ChangeCadence
  I-->>D: Wait / Cue / BlockedByCadence (+ cast)
  alt Kind == Cue
    D->>K: PullAt / TryPullPreferred (rotate only now)
    D->>S: UpsertLoadedCue(SwitcherCueDirection, clock)
    D->>D: CommitSentCue (pass-local consume · stage next)
  else Wait / Blocked
    Note over D,K: deck untouched · no Cue Mark moved
  end

the verdict

SyncedCueIntentKind: Wait (not in runway / already cued), Cue (in runway, cadence permits), BlockedByCadence (too soon after last change).

the event

CueEventIntent: Ordinary / Fill / Drop. Computed by comparing the Cue Mark to BeatManager Fill/Drop timing. Drop wins ties.

the casting

HandlesFill / HandlesDrop bias which Performer is pulled. Effect opt-ins today: Lightning = Fill+Drop, ColorSparkle = Fill.

The deck rule (no silent rotation). Decks are anti-repeat: draw from the top half, rotate the card to the bottom. Event casting inspects preferred candidates without mutating; the deck rotates only when a cue is actually sent. So a Wait or BlockedByCadence can never silently reorder the deck or change NextTransition. If a preferred Transition can't serve the Cue Mark now, the staged Transition is kept rather than delaying the cue.
Transition timing math. TransitionBeatPlan.FromCueMark: StartBeat = CueMark − Runway, ImpactBeat = CueMark, CompleteBeat = CueMark + Tail. Constraints: Runway, Tail ≥ 0 and Runway + Tail ≤ 12. Runway=0, Tail=0 is a valid hard cut; Runway=0, Tail>0 stays cueable through its tail so a skipped exact-beat frame can still start the transition backdated to the Cue Mark.

9 · The Switcher executes — fire-and-forget

The Director hands over one SwitcherCueDirection (Cue Mark beat, target effect, transition, repertoire) plus a tiny SwitcherClockSnapshot (current beat, beat fraction, seconds-per-beat, Unity time). Then it walks away. The Switcher owns the entire lifecycle from there.

B becomes current on V ≥ 1"]

A→B model

A = source effect, B = target, V = progress 0→1, D = 1−V. Progress is derived from wall-clock against the beat-derived start: V = (now − startTime) / durationSeconds. The Impact Point lands on the Cue Mark regardless of when the cue arrived within the runway.

edge behaviours

Late cue inside runway → backdated progress (impact still lands on beat). New move while one is in flight → previous B becomes the new source (last-command-wins). Zero duration → completes instantly.

Standalone uses the simpler ShowNow (cut) and explicit StartTransition with a wall-clock default duration; Synced uses only UpsertLoadedCue. Either way the Switcher derives its own lock/start/progress — the Director supplies beats, never Unity times.

10 · What the Director deliberately does not do

These negative-space rules are the architecture. Most of the "things changed that shouldn't have been" bugs are violations of one of these seams.

Does not read raw OSC / Track Phase fields — only the TimingFrame from On-Air Timing.
Does not inspect Switcher Loaded / Locked / Started status. Fire-and-forget; it records consumption from its own command.
Does not compute Unity start times, durations, lock points, or transition progress for Synced cues — that's the Switcher's.
Does not let Fill/Drop/Energy change cue timing — events bias casting only.
Does not rotate a deck unless a cue is actually sent.
Does not own the Cue Sheet — On-Air Timing builds/reuses it; the Director only reads CueMarkBeat.

And the converse, for the Switcher: it must not read Track Phase, choose Cue Sheets or Cue Marks, cast Performers, or select decks. It executes the one cue it was handed.

11 · Invariants worth memorising

  • Beats, not seconds. Everything musical is beat-denominated, counted from one, in powers of four (4 beats = 1 bar). Synced scheduling never does sub-beat ms math — the incoming OSC already carries the runway.
  • 16-beat minimum cadence. At least 16 beats (4 bars) between Performer changes, checked against the landing beat.
  • Changes land on the one. A transition's Impact Point lands on a Cue Mark (a phrase/phase boundary), never mid-bar.
  • Standalone is a preference, not a fallback. No-OSC behaviour is fully intentional self-running art, not a degraded path.
  • Core/editor two-layer rule. Director / Switcher / Repertoire / Cue / Hold are plain core C# with no UnityEditor dependency; inspection & live-tweak live in the editor layer (the Director Observatory in ControllerEditor).
