PENROSEART · ARCHITECTURE REVIEW

Property Drawers & Editor Scripts

Deepening opportunities in Assets/Editor/. The focus is locality and testability: the editor layer is where the wall's live state, the Waveform Pool, the rhythm queries, and the new Held Effect selector all get surfaced and edited — and right now most of that lives in one 1,286-line drawer with no internal seams.

BeatManagerDrawer fuses three concerns behind a single OnGUI: (1) reaching into the live wall and writing to it, (2) caching the Waveform Pool file, (3) ~30 hand-rolled IMGUI rendering helpers.

Its CustomPropertyDrawer external interface is genuinely small and deep — that is not the problem. The problem is it has no internal seams: the policy with real invariants (don't spawn a Controller; retarget the live effect; log every change) can only be exercised by driving 1,286 lines of immediate-mode GUI.

Two consumers already share WaveformPool, so pool IO is correctly factored. What is not factored: live-wall policy, the inspector's visual vocabulary, and the presentation of rhythm queries.

Candidates

CANDIDATE 1

Extract the live-wall selection policy as a deep, testable module

Strong

Files

BeatManagerDrawer.cs · TryGetLiveWall, ApplyWallSelection, ResolveDisplayVariant
Controller.cs · BeatManager.cs

Problem

The act of reading and changing what the wall is playing lives as private statics in an IMGUI drawer. ApplyWallSelection carries load-bearing invariants — guard on Controller.HasInstance so touching the wall never spawns a Controller GameObject; writing activeVariant must also poke CurrentBeatVariant to retarget the on-screen effect; every change must log. None of this is testable, and the same "change the wall safely" need now recurs for the Held Effect path (Escape → −1, dropdown → hold).

Solution

Introduce a small module — a "live wall" handle — whose interface is three things: TryGet(out WallState), SelectVariant(int), and DisplayVariant. The anti-spawn guard, the retarget-and-log behavior, and the Auto/locked resolution sit behind that seam. Drawers consume it; they no longer reach into Controller.Instance directly.

Benefits

  • Locality: the "don't spawn a Controller / retarget / log" rules live in one place, not scattered as a comment in a 1,286-line file.
  • Leverage: the Held Effect drawer and any future wall control get the safe-change behavior for free instead of re-deriving the guards.
  • Testability: the interface is the test surface — you can assert "select 3 → activeVariant 3, CurrentBeatVariant 3, one log line" without an IMGUI repaint.

Caveat (honesty): only one editor today pokes the wall directly, so by the strict "two adapters = real seam" rule this is borderline — but the second consumer is already arriving via Held Effect, and the payoff here is testability of real invariants, not just reuse.

CANDIDATE 2

A shared inspector-rendering vocabulary (meters · chips · swatches · panel · styles)

Worth exploring

Files

BeatManagerDrawer.cs · DrawMeter, DrawStatusChip, DrawSwatch, DrawPanelBackground, EnsureStyles, ~40 color tokens
EffectSelectorDrawer.cs · WaveformPoolEditor.cs (DrawPlot)

Problem

The "Penrose inspector look" — the track+fill+shine meter, the rounded status chip, the bordered swatch, the dark panel, the cached GUIStyle set, the color palette — exists only as private statics inside BeatManagerDrawer. EffectSelectorDrawer and WaveformPoolEditor each re-roll their own primitives. There is no shared visual module, so the look can drift and every new drawer starts from raw EditorGUI.

Solution

Lift the primitives into a small InspectorWidgets module: Meter(rect, value, color), Chip(rect, label, color), Swatch(rect, label, color?), Panel(rect, accent), plus the shared palette and styles. The shine/clamp/track math and color tokens live once, behind a tiny interface.

Benefits

  • Locality: change the meter shine or a band color in one module, every drawer updates.
  • Leverage: a new drawer learns four widget calls instead of EditorGUI.DrawRect math.
  • Depth: small interface, real implementation (AA, clamping, shine, style caching) hidden.

Seam reality check: two-and-a-half consumers exist (the dense BeatManager dashboard, the tiny Held Effect popup, the Pool plot). The dashboard is by far the heaviest user, so start by making its primitives public within the editor module and let the lighter drawers opt in — don't force the thin popup through a heavy widget API it doesn't need.

CANDIDATE 3

Move rhythm-query presentation to the data, not drawer "test seams"

Worth exploring

Files

BeatManagerDrawer.cs · BuildPhraseEventChipLabel, GetPhraseEventMeterValue, BuildPhraseEventReadout (marked "Test seam")
BeatManager.cs · PhraseEventInfo / Energy / Phase types

Problem

Three formatting functions are internal static precisely so tests can reach them — the textbook smell of "pure functions extracted for testability, but the bug lives in how they're called." Tests cross a seam that is past the drawer's real interface, into its private rendering helpers. The logic is presentation of a PhraseEventInfo (Fill/Drop), yet it lives away from the data it formats.

Solution

Give the contrived rhythm queries a presentation module co-located with their data — e.g. PhraseEventView(info) → { chip, meter, readout }. The drawer calls it; tests target it directly as a legitimate interface, not as a reached-around private.

Benefits

  • Locality: "how a Fill/Drop reads" sits next to what a Fill/Drop is.
  • Honest test surface: the interface you test is the interface the drawer uses — no internal back door.
  • Leverage: the same view formats the Beat dashboard and, later, any OSC/telnet/debug readout of the same queries.

Lowest-risk first cut. These are already pure functions with tests — this is relocation + renaming for locality, not new behavior. Pairs naturally with ADR-0002 (nullable rhythm queries): the view decides how null → "—" reads, in one place.

CANDIDATE 4

Waveform-Pool mtime cache — leave it (for now)

Speculative

EnsureWaveformPool reloads the pool only when the file's write-time changes — a genuinely deep little behavior. It's tempting to extract as WaveformPool.Cached.

But the deletion test says wait. The underlying IO (Parse / Serialize / ReadFileOrEmpty / FilePath) is already a shared module used by both the drawer and the Pool editor. Only the drawer needs the cache — one consumer. That's a hypothetical seam, not a real one. Extracting now adds an interface no second caller needs.

Revisit if a second live reader of the pool appears (e.g. an OSC-driven pool reload), at which point the cache becomes a real shared seam.

TOP RECOMMENDATION

Start with Candidate 1 — the live-wall seam

It is the highest-leverage move: it carves the one piece of real, invariant-bearing policy (don't spawn a Controller, retarget the on-screen effect, log every change) out of a 1,286-line drawer and puts it behind a three-method interface that is finally testable. It also establishes the editor↔runtime seam that the new Held Effect drawer — and every future wall control — should sit on, so the drawer count grows without re-deriving the guards. Candidates 2 and 3 then fall out cleanly against that spine.

If you'd rather take the lowest-risk first step, do Candidate 3 instead — it's pure relocation of already-tested functions and immediately removes the "tested around the interface" smell. Candidate 2 is the natural follow-on once a second drawer (Held Effect) proves the shared-widget seam is real rather than hypothetical.
