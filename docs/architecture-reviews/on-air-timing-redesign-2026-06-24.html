On-Air Timing redesign

2026-06-24 · On-Air Timing becomes a pure phase determiner · the 4-count is bedrock · phrase wins the grid · cue planning evicted to the Director

Thesis. Today one file (OnAirTiming.cs, 999 lines) tangles a universal job — determining phase, "where is the one" — with a Director job: cue planning. Split them. On-Air Timing's entire remit becomes phase determination, exposed as two deep modules: a reusable PhaseLock core and a PhraseTracker that rides on it. Cue planning (cue sheet, cursor, cadence) leaves for the Director. Everything else is downstream.

The model in one line. The 4-count is the clock we ground on; offset (where the one sits in the 16-grid) is held and re-latched only at structural triggers; phase position is recomputed every frame from the running beat against that held offset, so it tracks true playback — loops included — for free.

Status: design contract LOCKED with Hunter (grill of 2026-06-24). What remains open is empirical — a short list of facts to confirm on the rig (§9) — and the exact field list of the reading seam, which belongs in the ADR.

1 · The problem

OnAirTiming.cs welds two jobs at two altitudes:

  • Phase determination — "where is the one" on the 16-beat grid. Universal; every part of the runtime could use it.
  • Cue planning — CueSheetPlans / CueSheetCursor live as private classes inside the timing module, and pass-local cue memory round-trips through the Director every frame.

The interface is wide because the implementation does two unrelated things. Cue scheduling — a Director concern — leaks into phase locking. The only consumer is the Director, so nothing else can ask "where's the one?" And the deep-dive (on-air-timing-deepdive-2026-06-24.html) found the fallout: a stateless single-frame phase guess, a 3–15 beat loop "dead zone", and split-brain pass-local state owned half by the Director and half by timing.

The cut. On-Air Timing keeps only phase determination. The cue cursor, cue sheet, cadence, and all pass-local cue memory move to a Director-owned CuePlanner. What the Director does with phase is immaterial to the timing core — it just reads.

2 · Three altitudes — pulse, phase, phrase

Everything is powers of four. Three nested grids, each riding on the one below. The lowest is the one we trust.

Pulse — bedrock

The 4-count (beat_in_bar, 1-2-3-4). Always present, locally defined, and loop-invariant for any loop ≥ 1 bar. This is the clock we ground on — our advance driver. Ground, not inviolable: a sub-bar loop or DJ flub can perturb it, rarely. We detect that, we don't architect around it.

Phase — the one

The 16-beat grid (4 bars). "Where is the one." Expressed as an offset applied to the running beat: position = ((beat − 1) − offset) mod 16 + 1. Everything downstream — transitions, cue marks, effect downbeats — hangs off this.

Phrase — structure + look-ahead

Variable-length song structure (intro / build / drop …). It's the latch source for the one and it carries look-ahead (the next boundary and the next phrase's length). Normally a whole number of phases (length = N × 16).

The invariant: "phases in phrase." A phrase is normally a whole number of 16-beat phases, so every phrase boundary shares one mod 16 residue. When a phrase ends off the 16-grid from its own start, that violation isn't noise — it's the diagnostic: a non-power-of-two phrase, flagged as irregular (§6).
Currency: integer beats, end to end. Every timing metric the phase determiner holds or emits is a whole-beat integer — offset, phasePosition, beatsUntilNext, lengthBeats, phraseStart. The model is correct because it's exact integer modular arithmetic; floats would invite drift and fuzzy comparisons in grid math that must be crisp. The rhythm system's existing floats (progress, IntraBeatFraction, anticipation ramps) are BeatManager presentation-smoothing and stay out of the phase core.

3 · The model LOCKED

Bedrock. The 4-count drives. beat_in_bar plays two distinct roles we stop conflating: as the pulse it is the foundation (always there); as an anchor for the one it is the weakest signal (it can't tell which of the 4 bars carries the one). Today's PhaseClock ranks it weakest because it only judged the second role.

two quantities — the key split

  • offset — where the one sits in the 16-grid. Held. Re-latched only at structural triggers (§4).
  • phase position — where we are now. Recomputed every frame from the current beat against the held offset. It therefore tracks true playback: on a loop it rewinds with the music, by construction.

This split is what makes loops free: hold the offset, recompute position, and a backward jump just re-reads as the earlier grid position.

degradation — per layer, top-down, never loses the floor

  • Pulse — ≈always LOCKED while a clock exists. We always emit a usable 4-count.
  • Phase — LOCKED / COASTING / CONTRADICTED, independently.
  • Phrase — same three states, riding on phase.

Within synced mode there is no "Unlocked"; output is always consumable plus a trust signal. Confidence is the state enum (LOCKED / COASTING / CONTRADICTED), so the Director reads a trust level, not just on/off.

The floor — below the phase determiner. The "always locked" pulse assumes a clock exists. When there is no clock — the beat signals read -1 (no beat_in_bar/on-beat) — that is the trigger to reinstate stand-alone mode (the Director's free-running timer, dual-mode per ADR 0004). Falling through the floor is a mode exit, not a degraded phase state. Clock present but no phrase data stays in synced mode as COASTING / CONTRADICTED — and what to do there is the Director's call, not the timing core's.

4 · Anchoring & re-latch LOCKED

Bar identity — which of the 4 bars carries the one — has to come from a jumpy signal (the running beat or phrase_state); nothing stable carries it. So we sample it at structural moments and ride the pulse in between.

the rule

Phrase decides the grid. Latch offset from the phrase boundary when available (the phrase start is a one); with no phrase, fall back to beat mod 16 — offset 0 on the running beat (a guess). Then hold and recompute position off the running beat, cross-checked against the 4-count tick, until the next trigger.

Phrase wins as the latch source (only it says where a real one is); the 4-count wins as the driver (it's stable). We never chase phrase frame-to-frame.

re-latch triggers

  • Track-title change — reset: a new song is a clean slate (beat is a per-track counter, so the held offset is meaningless). Drop everything and re-acquire from the new song's first phrase; beat mod 16 covers the gap.
  • Phrase boundary — re-latch (confirm or correct the offset).

the gate

The gate is grounded on the tick, not the previous offset: a real phrase start is a downbeat, so accept a re-latch only if the grid the new offset implies agrees with the feed's beat_in_bar. A phrase start off the tick — or a held grid drifting off it (a sub-bar flub) — is noise → hold the old offset, flag CONTRADICTED. Anchoring on the tick (not "the offset shifted a whole bar from the last one") is what stays correct when the held offset is stale or the beat counter doesn't start on a downbeat. Track changes need no special case here — they reset first (see triggers).

Phrase-boundary detection. A boundary is detected when the derived phrase-start beat advances between frames: phraseStart = beat − (lengthBeats − beatsUntilNext); boundary ⇔ phraseStart ≠ phraseStart_prev. This is drift-immune and already computed in today's PhaseClock. We use it rather than a label change (adjacent phrases can share a label, so label-watching misses same-label boundaries) or watching beatsUntilNext hit 0 (fragile across dropouts).
Predict-then-confirm. phrase_state carries look-ahead — beatsUntilNext (when the next boundary lands) and lengthBeats (the upcoming phrase's size). Use it to pre-compute the next re-latch: where the next one lands, and whether the next phrase keeps us in-phase. At the boundary, a match is a clean confirmed re-latch; a disagreement is the contradiction flag. Enhancement, not dependency: if look-ahead is absent (null), fall back to react-at-boundary. Correctness never depends on look-ahead existing.

On track change: beat is a per-track counter, so the held offset — tied to the old song's counter — is meaningless on the new song. We reset and re-acquire from the new song's own phrase, with the beat mod 16 fallback covering the gap until its first boundary. No soft-hold, no cross-track carry; phase correctness never depends on cross-track state.

Recovery from CONTRADICTED / anomaly: it clears as soon as the grid agrees with the tick again — a phrase boundary that lands on the tick, or the pulse re-aligning. State is derived fresh each frame, so a contradiction never sticks; no separate timer.

6 · Loops & non-power-of-two phrases — handled for free

Loops — no explicit detection.

A loop is just a bar-aligned beat jump. The held-offset model swallows it: the offset is held, phase position recomputes from the rewound beat and tracks the music back. The 4-count continuity is the trust gate — bar-aligned ⇒ absorb silently; beat_in_bar breaks ⇒ Layer-0 anomaly. No loop detector, no dead zone, no cursor rewind.

Non-power-of-two phrase — phrase wins the grid.

A phrase whose length isn't a multiple of 16 (e.g. a 24-beat / 6-bar phrase) shifts the offset for everything after it — boundaries stop sharing a mod 16 residue, and only live phrase_state sees the drift. The re-latch-every-boundary rule handles it with no special case: each new phrase start becomes a one, the 16-grid re-aligns to the phrase.

Detection: if a phrase ends off the 16-grid from its own start (length ∤ 16), flag it irregular — that is the "phase ≠ phrase" event. We re-latch and keep driving; we record the irregularity for the Director. Lead-ins are the same mechanism: a constant offset the first phrase boundary establishes.

This retires the deep-dive's "3–15 beat loop dead zone" entirely: under held-offset + recomputed-position, phase survives every loop length by construction; the old code's brittle 16-beat backward-jump threshold was the wrong frame.

PhaseLock (core). Interface: BeatManager-projected integer values in, PhaseReading out. Implementation: held offset, the perturbation table, dead-reckoning, lock states. Deep — narrow interface over real behavior. It reads phrase numerics (boundary timing) directly; it does not depend on PhraseTracker.
PhraseTracker. Rides on PhaseLock's grid; adds song structure (label, next, position-in-phrase, length, look-ahead, irregular flag). Reads the one; never re-derives it. Keeps phase and phrase un-conflated by being a separate module.
Why the seam is justified, not speculative. The payoff is testability: a PhaseLock with a projected-values-in / PhaseReading-out interface can be property-tested against scripted DJ timelines — loops of every length, lead-ins, non-pow2 phrases, seeks, dropouts, track changes — independent of the Director. That harness is the leverage. Effect-level consumption is allowed to emerge; we add no extension points for hypothetical consumers (YAGNI). We build for the Director and the harness.

Input boundary: PhaseLock consumes BeatManager's already-projected integer values (the path OnAirTiming.ReadFrame takes today) — it does not re-parse OSC. Reading fields are ADR detail, not a design decision. Candidate phase fields: confidence (state enum), phasePosition, oneOfCurrentPhrase, beatsUntilNextOne, offset, barInPhrase, beatInBar, fourCountContinuous, irregularPhrase, provenance (source / reanchored / coasting). All integer-beat valued.

9 · What's unknown — verify on the rig

The design is locked; these are empirical facts about the gear that tune it. None blocks writing the ADR or the test harness.

  • Does phrase_state arrive before the boundary? Predict-then-confirm needs the upcoming phrase's lengthBeats (and beatsUntilNext) populated ahead of the boundary. If it only flips at the boundary, we degrade gracefully to react-at-boundary — but confirm which we get.
  • Does RaveSystem always send phrase data? If beat-without-phrase actually occurs on your rig, the beat mod 16 (offset 0) fallback carries more weight than expected.
  • Phrase-boundary timing reliability vs the beat clock. "Phrase wins the grid" and the bar-alignment gate assume phrase boundaries are accurate and bar-aligned. If phrase detection is noisy on your gear, the gate's sub-bar-jump rejection earns its keep — confirm the noise profile.
  • How often does the 4-count actually wobble? Sub-bar loops / flubs are the only thing that perturbs the bedrock. If they're vanishingly rare, the single Layer-0 anomaly flag is enough; if not, we'd consider a richer recovery.
  • phrase_state.remaining unit. Read as "remaining phrase changes (count)"; confirm before any end-of-track use. Not phase-critical.
