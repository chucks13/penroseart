Candidates

These are optimization and deepening candidates. They do not propose public runtime behavior changes.

Candidate 1

Make the Play Mode repaint path allocation-light

Strong in-process polish

Files

Assets/Editor/BeatManagerDrawer.cs
Assets/Editor/WaveformPlot.cs
Assets/Editor/ControllerEditor.cs

Problem

Play Mode makes ControllerEditor repaint constantly, and the expanded BeatManager drawer allocates avoidable objects during those repaints.

Solution

Cache the Waveform selector option array, cache query-label GUIContent instances, and reuse the WaveformPlot point buffer.

Wins

  • locality: repaint caches concentrate
  • leverage: plot fix helps two callers
  • interface unchanged
  • safe polish scope

Before

DrawWaveformSelector
new string[] every repaint
DrawQueryRowLabel ×7
new GUIContent each row
WaveformPlot.Draw
new Vector3[129]

After

Waveform options cache
rebuild on Pool stamp / label change
Static query labels
tooltip text allocated once
Static plot buffer
same points, refilled on repaint

Candidate 2

Give BeatManagerDrawer internal seams

Worth exploring in-process deepening

Files

Assets/Editor/BeatManagerDrawer.cs
Assets/Tests/Editor/BeatManagerDrawerVisualModelTests.cs
Assets/core/BeatManager.cs

Problem

The drawer has a deep external interface, but its implementation is one large class: live query reads, wall selection, layout, widget drawing, formatting, Pool cache, and child fields all sit behind OnGUI.

Solution

Keep the Unity PropertyDrawer as the host, then move pure display decisions into a dashboard visual model and keep IMGUI drawing in a renderer module.

Wins

  • interface stays one drawer
  • tests hit visual model seam
  • locality: row rules concentrate
  • implementation absorbs helpers

Candidate 3

Concentrate no-spawn Play Mode access

Worth exploring in-process seam

Files

Assets/Editor/BeatManagerDrawer.cs
Assets/Editor/PenroseTuningWindow.cs
Assets/core/Controller.cs

Problem

Two editor modules already carry the same important guard: check Application.isPlaying and Controller.HasInstance before touching Controller.Instance, because touching it too early can spawn a Controller GameObject.

Solution

Add a tiny editor-only live Controller access module, then put wall variant selection behind an owner-aware method that reuses that access rule.

Wins

  • two adapters justify seam
  • locality: anti-spawn rule
  • leverage: future steering
  • tests avoid IMGUI

Candidate 4

Delay a shared inspector widget module

Speculative in-process YAGNI

Files

Assets/Editor/BeatManagerDrawer.cs
Assets/Editor/WaveformPlot.cs
Assets/Editor/WaveformPoolEditor.cs

Problem

The BeatManager drawer owns many private visual primitives, but other editor modules mostly use default Unity fields. Extracting a broad widget module now risks making a shallow module.

Solution

Keep WaveformPlot shared, because it already has two callers. Do not extract chips/meters/swatches until a second custom dashboard needs them.

Wins

  • one adapter stays hypothetical
  • deep module only when earned
  • locality remains clear
  • no broad module churn

WaveformPlot
deep enough: grid + AA polyline + playhead behind one Draw call
BeatManager widgets
private to one dense dashboard

Later, if earned

InspectorWidgets
Meter · Chip · Swatch · Panel · styles

Require a second dense dashboard before making this seam real.

Non-candidate findings

EffectSelectorDrawer is already small

The deletion test says it earns its keep: delete it and the Held Effect int leaks Random/index mapping into the Inspector user. No refactor recommended.

WaveformPoolEditor already avoids log spam

Draft rows store raw strings, delayed text commits trigger parse, and sliders update cached previews. Keep this shape.

Documentation drift

ADR-0001 and CONTEXT.md still say the Pool is edited by a property drawer. Current code uses WaveformPoolEditor plus the BeatManager dashboard selector.

Top recommendation

Start with allocation-light repaint polish

Tackle Candidate 1 first: it is behavior-preserving, bounded to two editor files, helps the continuously repainting dashboard immediately, and does not force a new seam before the deeper BeatManager dashboard split is justified.
