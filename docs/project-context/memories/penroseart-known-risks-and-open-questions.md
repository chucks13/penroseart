# PenroseArt Known Risks and Open Questions

These are confirmed from local code/assets unless marked as a question. Do not silently "fix" behavioral items without confirming intent because many affect hardware output or visual style.

## Output path state

- Current active code has file-local `#define ENABLE_SERIAL` in `Assets/core/Controller.cs:2`, so runtime uses USB serial output through `SerialOut`.
- Root `CONTEXT.md` and `Assets/core/helpers/CONTEXT.md` have been realigned to describe serial as the active path while noting that the ACN/E1.31 UDP fallback code still exists.
- Ask which path is production before changing output code.

## API compatibility and serial output

**Updated 2026-05-21:** Standalone is now `apiCompatibilityLevelPerPlatform: Standalone: 6` (`NET_Standard_2_1`), not `.NET Framework 4.8`. The project ships platform-specific `System.IO.Ports` 6.0 runtime assets under `Assets/Plugins/System.IO.Ports/runtimes/`. This is the path documented in `[[penroseart-netstandard-serial-transport-options]]`.

Current desktop runtime asset shape:

- macOS: Unix managed runtime DLL plus a universal x86_64+arm64 `libSystem.IO.Ports.Native.dylib`, importer-restricted to macOS Editor/Standalone.
- Windows: Windows managed runtime DLL, importer-restricted to Windows Editor/Standalone. The inspected NuGet package did not include a separate Windows native runtime asset.
- Linux: Unix managed runtime DLL plus Linux x64 `libSystem.IO.Ports.Native.so`, importer-restricted to Linux Editor/Standalone.

Caveat: Android/iOS/WebGL serial support remains out of scope, and `Controller.cs` still file-defines `ENABLE_SERIAL`, so platform-gating serial code is still a future cleanup if non-desktop builds matter.

See `[[penroseart-netstandard-switch-compile-errors]]` for the prior failure mode (now superseded) and `[[penroseart-investigation-2026-05-21]]` for the corrected state.

## Serial protocol drift

`Assets/core/S2_MINI_PROTOCOL.md` and `Assets/core/SerialOut.cs` disagree in details:

- Protocol doc connection settings say baud `2000000`, but Arduino strategy section says `Serial.begin(230400)`.
- `SerialOut.Init(230400)` is called, but `SerialOut.Init()` ignores its argument and sets `targetBaudRate = 2000000`.
- Protocol doc says the PC side includes a 200ms boot delay; current code waits 2 seconds.
- Current code appends `CMD_LATCH` (`0x4C`) after data packets; the doc's Data Packet section says Arduino immediately calls `FastLED.show()` after receiving RGB data.

Confirm firmware source/contract before changing serial output.

## Beat variant mismatch

Docs/readme describe beat variants as:

- `0`: every beat
- `1`: beats 1 and 3
- `2`: beats 2 and 4
- `3`: measure start
- `4`: 8th notes
- `5`: 16th notes
- `6`: syncopated

`BeatManager.GetBeatBrightness()` currently maps `case 5` to 8th notes, `case 6` to 16th notes, and `case 4` to syncopated. Current code comments document that mapping; clarify desired musical behavior before changing cases.

## Effect instance lifecycle nuance

The README says each effect has one instance and is never destroyed. That is true for `Controller.SetupEffects()` top-level catalog entries, but mixers/wrappers create transient child effects on activation:

- `Mirror.OnStart()` creates and initializes `sourceEffect`.
- `RandomEffectsMixer.OnStart()` creates 2-3 child effects.
- Other mixers create children and may suppress or unify beat behavior.

Do not assume there is only one instance of a concrete effect type globally.

## Reflection order is unsorted

`Factory<T>` returns reflected types without explicit sorting. Adding/removing/renaming concrete subclasses can shift:

- effect order,
- transition order,
- keyboard shortcut mapping,
- deck order,
- the meaning of serialized `currentTransition` indexes.

If deterministic catalog order matters, introduce explicit sorting only after confirming visual/operational expectations.

## Scene data source ambiguity

`Penrose.Awake()` reads JSON from scene-serialized `Controller.jsonSource`, and investigation verified that this scene blob currently matches `Assets/StreamingAssets/rawdata.json`.

Open question: should scene-serialized `jsonSource` remain the source of truth, or should runtime load from `StreamingAssets/rawdata.json`?

Changing this affects editor usability, runtime file access, Android/StreamingAssets behavior, and risk of scene corruption.

## Runtime side effects during Play Mode

Running the scene can dirty or affect the machine:

- Serial output scans/opens serial ports because `ENABLE_SERIAL` is file-defined.
- OSC/UDP listeners open ports `6969`, `7778`, and `8500`.
- `kscope` rewrites `Assets/StreamingAssets/images/*/files.txt` on non-Android.
- If `ENABLE_TELNET` is enabled, telnet listens on port `23` and appends to root `log.txt`.

Tell future agents to ask before running Unity Play Mode if hardware or working-tree cleanliness matters.

## Thread lifecycle and error visibility

Potential maintenance risks:

- `UDPReceive.ReceiveData()` loops forever and swallows exceptions.
- `OSCReader.Close()` uses `Thread.Abort()`.
- `SerialOut.BoardIOThreadLoop()` catches all exceptions and marks a board not ready without surfacing detailed failure state.
- `Controller.sendUDPFrame()` does not await `sendACN()` tasks.

These are not necessarily current bugs, but they matter for reliability/hardware debugging.

## Unreachable or suspicious code

- `Panels` chooses `which = Random.Range(0, 2)`, so `case 2` branches appear unreachable because Unity integer `Random.Range(0, 2)` returns 0 or 1.
- `Controller.startEffect` is serialized but current `SetupEffects()` ignores it.
